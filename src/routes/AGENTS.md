# Routes (AppGen)

Use this guide when creating or editing route pages in `src/routes/`.

## Route conventions

- Create routes with `createFileRoute` and keep files focused on page composition.
- Do not edit `src/routeTree.gen.ts` manually (auto-generated).
- **The home route `_protected/index.tsx` is the app's main page.** It ships as a "Welcome…" placeholder and is what the preview opens to (`/`). Build the primary/first page by replacing this file directly — never leave the placeholder, and never put the main page on a separate route while `/` still shows "Welcome…". Rename the matching `Dashboard` entry in `src/components/layout/index.ts` instead of adding a duplicate `/` entry.
- For sidebar pages, add/update the route entry in `src/components/layout/index.ts` so nav and breadcrumbs stay in sync.
- Keep user-facing copy plain and short. AppGen users are non-technical.

## Maintainability rules

- Do not hardcode tenant-specific values (repo names, IDs, account names, URLs) directly in UI text or API calls. If the user provides a URL or repo name as part of their request, put it in a typed constant at the top of the server router file (or better, a `z.url()` procedure input) — never paste it directly into JSX text or hardcode it in two places. UI display labels should derive from the same source, not be re-typed.
- For tRPC procedure calls in routes: follow the `useTRPC` + `queryOptions`/`mutationOptions` pattern. See [`/base/src/integrations/trpc/AGENTS.md`](/base/src/integrations/trpc/AGENTS.md) for the required usage (base-owned; read on demand).
- Prefer existing hooks/services first (the platform hooks in `src/hooks/` and shared services under `@/services/*` already cover auth, connectors, workflows, chat); avoid adding duplicate fetch logic in route files.
- If a page repeats card/row/section markup, use a typed config array or small reusable component.
- Every data page must explicitly handle loading, empty, success, and error states.
- Keep route files readable; split large pages into local view components/hooks when needed.

## Feature handoff notes (required)

When you add a new feature route, append a short subsection here with:

1. Goal and user-visible behavior.
2. Data flow (UI -> hook/service -> API/DB).
3. Inputs/configuration (route params, constants, env, IDs).
4. Constraints or known limitations.
5. Validation commands run (`bun run check`, `bun run build`, `bun run test`).

**Definition of done:** The feature is not complete until the Feature notes subsection below is updated with actual content (not the placeholder line). Writing "Let me update the AGENTS" without then editing this file does not count.

## Feature notes

### ResilienceTwin GeoAI v0.6 — dispatch simulator

1. **Goal / behavior.** Home route (`/`) is a logistics dispatch simulator for two ports (LA, Long Beach) and
   five warehouses (Carson, Commerce, Ontario, Riverside, Fontana): KPI cards, an ArcGIS map, a Scenario
   Assistant chat, a shipment plan table, an exceptions/recovery table, and customer outreach — all driven
   from one computed scenario result. `/data-feed` is a secondary page for the bundled IoT/disruption replay
   console (ingestion validation, live telemetry, event log).
2. **Data flow.** `src/server/db/schema.ts` (facilities, trucks, drivers, shipments, warehouse slots, road
   graph, iot/disruption events, truck/corridor live state, outreach notices, scenario chat log) ← seeded from
   CSV + NDJSON fixtures under `src/server/db/seed-data/` via `bun run db:seed`. The routing/scheduling engine
   (`src/lib/resilienceTwin/{engine,network,constants,types,scenarioParser,assistantReplies,exports}.ts`) is a
   pure, DB-agnostic TypeScript port of the reference ResilienceTwin GeoAI v0.6 Python optimizer — validated in
   `src/lib/resilienceTwin/__tests__/engine.test.ts` and cross-checked against the reference's own
   `scenario_evidence_v06.csv` (byte-identical scheduled/cost/CO₂ output for Normal and Highway-slowdown
   scenarios). `src/services/db/*Service.ts` are the only files that touch the database (`createServerFn`
   handlers), called from `src/hooks/useResilienceTwin.ts`. The Scenario Assistant calls the user-selected
   `Bolt_instruct_v2` AI/ML connector via `useExecuteModel` (already server-mediated — the key never reaches
   the browser) to extract settings, with an always-available demo-mode regex fallback
   (`src/lib/resilienceTwin/scenarioParser.ts`); the actual result explanation is always templated from the
   computed scenario (`assistantReplies.ts`), never generated by the model, so shipment IDs/costs/ETAs in chat
   are never invented.
3. **Inputs/configuration.** No route params. Diesel reference price $4.10/gal (`COST_PARAMETERS` in
   `src/lib/resilienceTwin/constants.ts`); named-highway → modeled corridor mapping is fixed
   (`HIGHWAY_SEGMENT_MAP`, e.g. Highway 60 → `S-005`) and always labeled a proxy in the assistant and on the
   map. AI connector name (`Bolt_instruct_v2`) is a constant in `scenario-assistant.tsx`, resolved to an id at
   runtime via `useConnectors` — never hardcode the id. Map basemaps are public, key-less Esri world basemap
   REST services loaded through the real ArcGIS Maps SDK for JavaScript (CDN build, `src/lib/resilienceTwin/arcgisLoader.ts`);
   no ArcGIS API key is configured, so ArcGIS Routing / premium vector basemaps are out of scope — routing uses
   the bundled synthetic 9-node/13-segment road graph instead, labeled as illustrative everywhere it's shown.
4. **Constraints / known limitations.** Reference's 27-table dataset was trimmed to the tables the brief's
   acceptance tests touch (fleet, drivers, shipments, slots, road graph, cost/emission constants, 6 scenario
   definitions); staff roster, skills, dependency graph, community zones, and audit-log tables were not
   ported. No RBAC — single shared dispatcher view. Replay runs as a server-side ingestion job triggered from
   `/data-feed` (no native streaming connector on this platform). Playwright is unavailable in this sandbox
   (`Chromium distribution 'chrome' is not found`), so the map/chat/table wiring was verified via `tsc --noEmit`,
   Vitest, and manual review rather than an end-to-end browser run — see the test report delivered in chat.
5. **Validation commands run.** `bunx biome format --write <touched files>` throughout; `bunx tsc --noEmit -p
   tsconfig.app.json` (clean); `bun run test` (all suites passing, including the new engine unit tests);
   `bun run db:status` / `db:seed` after schema changes. `bun run build` run once at the end as a publish check.
